# 项目现状与后续计划

## 截至 2026/8/30 14:12 的项目现状

当前项目已经具备一套完整、可运行的多轮商品搜索流程。Agent 能理解用户逐步补充的要求、维护对话状态，并结合精确匹配、BM25 和可选的语义搜索，从 50,000 件商品中返回 Top 10 推荐。

目前离线方案在 200 个公开测试案例中通过了 199 个，Hit Rate@10 为 0.995，唯一失败的是 `public_0020`。加入 Qwen Dense Retrieval 后，主要改善了部分目标商品在推荐列表中的位置，但整体提升较小。现有方案仍然以 lexical search 为主，语义搜索只起辅助作用。

系统当前的优势是稳定、可复现，而且即使远程模型不可用，也能回退到离线检索。主要不足是策略比较固定：buying 和 browsing 基本走同一条流程，用户画像利用很少，追问几乎只使用 `other`，LLM 除了 Embedding 和可选的 Query Rewrite/Rerank 外，没有真正参与意图理解、策略选择或失败恢复。

接下来的重点不应该只是让更多环节使用 LLM，而是让每项新能力都解决一个明确问题，同时避免破坏目前已经通过的 199 个案例。

## 1. 唯一失败案例：public_0020

### 目前识别到的问题

`public_0020` 是当前唯一没有在 10 轮内找到目标商品的案例。目标是一件带有 Grandma 文案的长袖 novelty T-shirt，同时也可以被理解为女士服装、家庭礼物或母亲节礼物。它的身份信息比较模糊，评分数量也很少，很容易被大量相似商品压到后面。

目前还不能直接断定这是语义搜索、排序或提问策略的问题。它可能是目标从未进入候选范围，也可能是进入候选后排名不够高，或者用户在整个对话中没有提供足够的信息来区分它。

### 我们 propose 的解决方案

先把这个案例作为完整的 failure study，确认问题属于候选召回、最终排序还是信息不足。只有完成归因后，再决定应该优化检索、调整排序、改善追问，还是加强候选轮换。

修复时不能只关注它是否成功，还要确认原来通过的案例不会因此退步，避免为了一个公开案例造成整体过拟合。

### 我们的发现

复盘后确认，目标商品一直在候选榜单中，但最终只排在约第 214 名，因此这不是召回失败，而是排序和信息不足共同造成的问题。

公开 evaluator 只会从预先生成的 attribute 中回答问题。对于这个案例，Agent 最终只能获得 cotton、grey、通用材质说明和 Imported。这些信息同时存在于大量相似商品中，而真正能区分目标的 Grandma、文字图案、Mother's Day gift 和 long sleeve 等信息不会被 evaluator 披露。

因此，单纯增加 LLM、延长上下文或继续询问 attribute，都无法凭空恢复缺失的信息。Public evaluator 更像 bare-minimum test，但我们仍希望系统能够兼容更自然、信息更丰富的真实用户或 private conversation。

### 我们最终的解决方案

采用兼容两种场景的双轨策略。

Agent 首先用自然语言询问更有区分度的信息，例如文字或图案、送礼对象、使用场合和具体款式，同时继续输出 evaluator 能理解的结构化 `ask_attribute`。真实用户可以补充 Grandma、Mother's Day gift 等关键信息；低版本 evaluator 仍然可以按照 attribute contract 正常回复。

如果用户或 evaluator 无法提供更多信息，Agent 就判断信息已经耗尽，不再重复无效追问，而是进入探索模式。探索模式应优先考虑完整 attribute 组合，降低通用 popularity signal 对低评论商品的压制，并从不同商品 identity 或 use-case 的候选簇中选择不重复的结果，最大化 10 轮内的有效覆盖率。

这套方案不能在缺乏信息时保证唯一识别目标，但它不会针对 `public_0020` 写死规则，同时能够兼容 bare-minimum evaluator 和更自然的未来对话。

#### Clarification Policy：如何决定下一步问什么

Intent recognition、user profile 和 ask-attribute 不应被当成三个完全独立的功能。它们需要共同组成一个统一的 Clarification Policy。

每一轮，Agent 先判断用户是在明确购买还是仍在浏览，再排除用户已经回答或拒绝过的问题。User profile 用来提示用户通常重视哪些维度，当前候选商品之间的主要差异则决定什么问题最有区分度。最终问题由这三部分共同决定：用户还没有说什么、什么信息最能区分当前候选，以及用户通常最关心什么。

系统应先决定“问什么”，再生成自然的表达，同时输出 evaluator 能理解的 `ask_attribute`。LLM 可以帮助把问题说得自然，但不应脱离当前候选和对话状态随意决定策略。

#### `public_0020` 的理想完整流程

用户最初只说明需要 Novelty Women clothing，并要求 cotton。Agent 已经知道 material，因此不应重复询问材质。当前候选的主要区别是文字或图案、送礼对象、使用场合和具体款式，所以 Agent 可以自然地询问：是否有偏好的文字、图案、送礼对象或场合，同时使用 `other` 作为兼容 evaluator 的结构化字段。

如果面对自然用户，用户可能补充 Grandma、long sleeve 或 Mother's Day gift。Agent 获得这些高区分度信息后，就能把目标商品排到前面。

如果面对 bare-minimum evaluator，它仍然只会返回 grey、通用材质说明和 Imported。Agent 应识别到这些信息仍不足以区分目标，并在可用 attribute 耗尽后停止重复追问，转入多样化探索：优先完整匹配已知属性，同时从不同文字设计、使用场合、款式和商品 identity 的候选簇中选择不重复的结果。

因此，系统形成两个向后兼容的分支：自然用户通过开放但有针对性的问题提供更多语义信息；简单 evaluator 无法提供更多信息时，Agent 自动切换为最大化候选覆盖率的探索策略。后一个分支只能提高命中概率，不能在缺乏证据时保证唯一识别 `public_0020`。

## 2. User intent recognition：Buying 与 Browsing

### 目前识别到的问题

系统目前能够从特定句式识别 browsing，但识别结果没有真正改变后续策略。Buying 和 browsing 仍然使用基本相同的提问、检索和排序流程。

Buying 用户通常有较明确的购买目标，需要重视硬性要求和准确匹配；browsing 用户仍在探索，更需要多样化推荐和方向性的引导。两类用户如果完全使用相同策略，体验和检索效果都不理想。

### 我们 propose 的解决方案

为 buying 和 browsing 建立不同的 high-level 策略。Buying 模式强调明确约束、准确匹配和快速收敛；browsing 模式强调探索、推荐多样性，以及帮助用户逐渐明确需求。

LLM 可以作为不明确场景下的意图判断工具，但不应该取代所有简单、可靠的规则。重点不是增加一个标签，而是让这个标签真正影响后续行为。

## 3. User profile 蒸馏与使用

### 目前识别到的问题

用户画像并非完全没有使用，但目前只以很低的权重参与 lexical ranking，而且没有进入 Dense Query。

更重要的是，现有画像通常只说明用户重视哪些维度，例如 material、fit 或 comfort，并没有说明用户具体喜欢 cotton、宽松版型或某个品牌。直接把这些抽象标签当成商品偏好，可能会产生错误的排序信号。

### 我们 propose 的解决方案

将用户画像整理成两类信息：用户重视的决策维度，以及有明确证据支持的具体偏好。

“重视 material”这类信息应该主要用于决定下一步问什么；“偏好 cotton”这类明确偏好才适合进入搜索和排序。当前对话中用户明确表达的要求始终应该高于历史画像，避免画像覆盖本次真实意图。

## 4. Context 与 Memory Management

### 目前识别到的问题

当前对话最多只有 10 轮，而且系统主要使用结构化状态，而不是持续把完整对话发送给 LLM。因此目前还没有明显的上下文长度问题。

不过，随着后续引入更多 LLM 能力，历史消息、用户约束、否定信息和意图覆盖可能逐渐变得难以管理。简单截断旧消息可能会丢失重要要求，也可能重新引入已经被用户否定的偏好。

### 我们 propose 的解决方案

继续以结构化状态作为长期记忆的核心，只保留少量近期原始对话作为补充。无论如何压缩上下文，都应优先保存当前有效约束、用户明确否定的内容、已经问过的问题，以及被新要求替代的旧偏好。

这项工作应在 LLM 真正开始使用更多对话历史后再推进，目前不是最高优先级。

## 5. Prompt Self-Evolution 与失败感知

### 目前识别到的问题

LLM 目前没有真正参与策略判断，Agent 也无法识别自己是否正在重复无效推荐、是否没有获得新信息，或者检索结果是否已经停滞。

但在线运行时，Agent 并不知道 ground truth，因此它不能真正确定自己“推荐错了”。如果让模型自由修改 prompt 或策略，系统会变得难以复现，也容易发生不可控的行为漂移。

### 我们 propose 的解决方案

让 Agent 感知可观察的失败信号，而不是猜测 ground truth。例如用户持续不满意、推荐结果高度重复、候选范围没有缩小、约束互相冲突，或多种检索方式给出严重不同的结果。

发现这些信号后，Agent 应从有限、明确的恢复策略中选择下一步，例如重新确认需求、改变提问方向、放宽软性偏好或增加候选多样性。Prompt 的演进更适合在线下基于失败记录进行，并在完整回归测试后才接受新版本。

## 6. Ask Attribute 不能只问 `other`

### 目前识别到的问题

当前系统几乎每一轮都询问 `other`。这种做法在公开 evaluator 中非常有效，因为它能一次获得尚未披露的多种要求，但从真实对话体验来看过于笼统，也没有利用已有画像和候选商品信息。

如果直接全面改成询问具体属性，又可能降低公开评测成绩，因为具体问题只能获得对应类型的信息，有时用户并没有该方面的偏好。

### 我们 propose 的解决方案

采用混合追问策略。优先根据用户画像、当前意图和候选商品之间最有区分度的属性来提出具体问题；当无法判断最有价值的问题，或者具体问题没有获得有效信息时，再使用 `other` 作为 fallback。

Buying 用户应优先确认影响购买决策的硬性要求；browsing 用户则更适合从 style、use case 或更细的品类方向开始探索。

## 7. Semantic Search 与各部分权重

### 目前识别到的问题

当前融合中 lexical search 占据绝对主导地位，Dense Retrieval 主要用于小幅调整排名。现有公开结果显示 Dense Retrieval 确实带来了一点 MRR 提升，但没有提高最终命中数量。

用户画像的排序权重也非常低。不过，简单提高 Dense 或 profile 权重并不一定更好：精确品牌、材质、尺寸和预算通常更适合 lexical/exact match，而抽象风格、使用场景和同义表达更适合 semantic search。

### 我们 propose 的解决方案

从固定权重逐步转向根据 Query 类型和检索信号调整权重。明确、具体的购买约束继续以 exact 和 lexical 为主；模糊的 browsing、style 和 use-case 查询可以适当提高 semantic search 的作用。

用户画像应作为低于当前明确意图的软信号，并区分“关注某个维度”和“明确喜欢某个值”。所有权重调整都应通过完整案例集比较，而不是只根据单个失败案例或表面上的权重比例判断。

## 建议实施顺序

建议按照以下顺序推进：

1. 分析 `public_0020`，明确唯一失败案例的真正原因。
2. 将 intent recognition、user profile 和 ask-attribute 合并为统一的 Clarification Policy，同时保留 `other` fallback。
3. 让 buying 和 browsing 通过 Clarification Policy 使用真正不同的提问与探索策略。
4. 蒸馏和规范化 user profile，先用于指导提问，再谨慎进入检索。
5. 在前面几项稳定后，重新评估 lexical、dense 和 profile 的融合权重。
6. 当 LLM 开始使用更多历史信息后，再完善 context 和 memory management。
7. 最后增加受约束的失败感知与恢复机制，再考虑离线的 prompt evolution。

每一步都应单独评测，并比较总体指标、不同 scenario 的表现、新修复案例以及新增 regression。当前系统已经达到 199/200，因此“保持已有能力”与“增加新能力”同样重要。
